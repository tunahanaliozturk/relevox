# Built-in behaviours with nothing to do

Same machine and harness as M4:

```
BenchmarkDotNet v0.15.8, Windows 11 (10.0.26100.9448/24H2)
Intel Core Ultra 7 255H 2.00GHz, 16 logical and 16 physical cores
.NET SDK 10.0.402, runtime .NET 10.0.13, X64 RyuJIT x86-64-v3, DefaultJob
```

M4 left one cost open. Once an application configures a pre- or post-processor, or has an exception handler,
MediatR adds its built-in behaviours to every request, and so did Relevox. For the many requests those
behaviours have nothing to do for, Relevox resolved them on every send, each looking up its processors or its
exception catalog, then dropped them and copied the behaviour array without them.

The new row measures exactly that: the pipeline send with three behaviours, in an application that also
configures a pre- and a post-processor for a different request
([`BuiltInBenchmarks`](../../benchmarks/Relevox.Benchmarks/Benchmarks.cs)).

## Before and after

Measured on the same machine, at the commit that added the benchmark (e8f0599, 8efb82f after a rebase) and
after the review fixes below (the commit after cf6479e). Only Relevox's own columns compare across runs:
MediatR's moved by up to a fifth between them, which is the noise on this machine.

| | Before | After |
|---|---:|---:|
| MediatR 12.5 | 240.1 ns, 1088 B | 199.0 ns, 1088 B |
| **Relevox, typed** | 122.3 ns, 592 B | **86.5 ns, 456 B** |
| Three behaviours, no built-ins, Relevox | 58.3 ns, 392 B | 59.0 ns, 392 B |

The time Relevox saved is between a quarter and a third of the send, depending on the run; the 136 bytes are
the behaviours it no longer creates. Within each run, Relevox took about half of MediatR's time before and
about two fifths after. The send with no built-ins is unchanged: 55 to 59 ns across every run here.

## How

The built-ins are now registered as slots: singletons with no dependencies, in the place the real behaviour
would take, so their order among the application's own behaviours is unchanged. The first send of each
request type asks every slot whether its behaviour has anything to do for that request and remembers the
answer. From then on the idle slots are left out of the array the pipeline gets, and the others are replaced
by their behaviours, created as before.

## What the review changed

A review found two shapes the first version got wrong. A container whose scopes register behaviours of their
own, as Autofac's child scopes can, returned a longer list than the one a request's plan was learned from, and
the send failed; a plan that no longer fits is now worked out again for that send. And a behaviour that is not
`async`, registered before `AddRelevox`, sat outside an idle built-in: under MediatR it sees a faulted task from
the handler and never a throw, and that idle built-in is now kept as a shared pass-through that awaits.
Differential scenarios hold both timings.

## A version that was faster and lost

The first version skipped idle slots in place, with a 64-bit mask the pipeline read, so no array was copied:
73 ns and 416 B on the new row. It also put the mask in the pipeline's chain object, which every pipelined
send allocates, and the common send with no built-ins at all went from 58 ns to 70 ns and from 392 to 400
bytes. Copying the array costs only the requests that have slots, so that is what shipped.
