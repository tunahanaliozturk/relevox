# Moving from Mediator to Relevox

This guide is for projects on [Mediator](https://github.com/martinothamar/Mediator) (martinothamar/Mediator)
3.x, the source-generated library. Projects on MediatR have [their own guide](migration.md).

Mediator is further from Relevox than MediatR is. Its handlers return `ValueTask`, it has commands and queries
beside requests, a behaviour's `next` takes the message, and `AddMediator` configures one lifetime for
everything. A code fix, **Move from Mediator to Relevox**, rewrites the common shapes of all of that in one
pass ([ADR 0024](adr/0024-moving-from-mediator.md)). This page is the steps, what maps to what, what the fix
leaves for you, and what behaves differently afterwards.

Everything below was done to a real application first: the Blazor Clean Architecture template, on Mediator
3.0.2, with its 53 tests passing before and after. The write-up is in
[migration-trial.md](migration-trial.md#blazor-clean-architecture-on-mediator).

## Before you start

- **.NET 10 or later.** Relevox's packages target `net10.0` ([ADR 0003](adr/0003-net10-only.md)); the trial
  application targets `net11.0` and used them as they are.
- **Mediator 3.x.** The fix is written against the names in `Mediator.Abstractions` 3.0.2.
- **Find every `AddMediator` call**, test projects included. Mediator generates `AddMediator` once, in the
  project with its source generator, as a public method any project can call. Relevox generates `AddRelevox` in
  each project that calls it, as an `internal` method. A second project that calls it gets a second mediator;
  see [step 5](#5-test-projects-and-other-addmediator-calls).
- **Find files that start with `// <auto-generated>`.** Scaffolding tools write that header on code you then
  keep by hand. Roslyn's *Fix all* skips such files, so they need [step 2](#2-scaffolded-files).

## 1. Packages

The project that calls `AddMediator` swaps `Mediator.SourceGenerator` and `Mediator.Abstractions` for `Relevox`,
which brings the source generator. Every other project that declares messages or handlers swaps
`Mediator.Abstractions` for `Relevox.Contracts`, which has no dependencies.

```diff
 <!-- the project that calls AddMediator -->
-<PackageReference Include="Mediator.SourceGenerator" Version="3.0.2">
-  <PrivateAssets>all</PrivateAssets>
-  <IncludeAssets>runtime; build; native; contentfiles; analyzers</IncludeAssets>
-</PackageReference>
-<PackageReference Include="Mediator.Abstractions" Version="3.0.2" />
+<PackageReference Include="Relevox" Version="..." />

 <!-- a project with messages or handlers, such as the domain -->
-<PackageReference Include="Mediator.Abstractions" Version="3.0.2" />
+<PackageReference Include="Relevox.Contracts" Version="..." />
```

Unlike Mediator's generator, which was `PrivateAssets="all"`, `Relevox` flows to the projects that reference this
one, test projects included. That is on purpose: a project downstream that has no handlers of its own and does
not call `AddRelevox` generates nothing and uses the referenced project's mediator.

## 2. Scaffolded files

If files you maintain carry an `<auto-generated>` header, mark them as not generated for the move, in
`.editorconfig`:

```ini
[src/Application/Features/Contacts/**.cs]
generated_code = false
```

RVX0017 is reported in such files either way, and the light bulb fixes them one at a time. Files a tool
writes, such as a source generator's `*.g.cs` or a `*.designer.cs`, are not reported at all. *Fix all* and
`dotnet format` skip a file Roslyn considers generated, whatever the analyzer does; with `generated_code =
false` and `--include-generated` in step 3, they are moved with the rest. The section can go once the move is
done.

## 3. Run the fix

After the package swap and a restore, the Mediator code the fix can move is marked with
[RVX0017](diagnostics.md#rvx0017), a suggestion that offers **Move from Mediator to Relevox**: names rooted at
`Mediator`, every `AddMediator` call, and each type in a shape the table below maps. A type it cannot map, such
as a `MessageExceptionHandler` subclass or a notification publisher, gets no diagnostic of its own; only the
compiler's errors point at it, and step 4 says what to write. In Visual Studio,
Rider or VS Code, choose *Fix all occurrences in: Solution* on any of them. From the command line, in the
solution's directory:

```bash
dotnet format analyzers YourSolution.slnx --diagnostics RVX0017 --severity info --include-generated
```

`dotnet format` only changes files below the directory it runs in. `--include-generated` matters only with
step 2. A `dotnet build` before the fix shows the compiler's errors and not RVX0017, because the compiler stops
running analyzers once there are errors; the IDE and `dotnet format` do run them.

On the trial application it took about a minute and changed 67 files. What it leaves is a compiler error each,
covered in step 4.

### What maps to what

| Mediator | Relevox |
|---|---|
| `using Mediator;` | `using Relevox;` |
| `IRequest<T>`, `ICommand<T>`, `IQuery<T>` | `IRequest<T>` |
| `IRequest`, `ICommand` | `IRequest<Unit>` |
| `IRequestHandler<TReq, T>`, `ICommandHandler<TReq, T>`, `IQueryHandler<TReq, T>` | `IRequestHandler<TReq, T>` |
| `IRequestHandler<TReq>`, `ICommandHandler<TReq>` | `IRequestHandler<TReq, Unit>` |
| `IStreamRequest<T>`, `IStreamCommand<T>`, `IStreamQuery<T>` | `IStreamRequest<T>` |
| `IStreamRequestHandler<TReq, T>` and the command and query forms | `IStreamRequestHandler<TReq, T>` |
| `INotification`, `INotificationHandler<T>` | the same |
| `IPipelineBehavior<TMessage, T>` | the same; `MessageHandlerDelegate<TMessage, T>` is `RequestHandlerDelegate<T>` |
| `IStreamPipelineBehavior<TMessage, T>` | the same; `StreamHandlerDelegate<TMessage, T>` is `StreamHandlerDelegate<T>` |
| `where TMessage : IMessage` | `where TMessage : notnull`, or dropped beside other constraints |
| `ValueTask<T>` and `ValueTask` returned by `Handle` | `Task<T>` and `Task` |
| `next(message, cancellationToken)` | `next(cancellationToken)`; `next()` for a stream |
| `next(message, cancellationToken).AsTask()` | `next(cancellationToken)` |
| `MessageExceptionHandler<TMessage, T, TException>` | `IRequestExceptionHandler<TMessage, T, TException>`, by hand (step 4) |
| `INotificationPublisher` | Relevox's, with another signature, by hand (step 4) |

A void command keeps `Unit`, so its handler's `return Unit.Value;` stays valid. In a `Handle` method that is not
`async`, the fix also rewrites what it returns: `new ValueTask<T>(x)`, `new(x)` and `ValueTask.FromResult(x)`
become `Task.FromResult(x)`, or `x` itself when `x` is a `Task<T>`, `ValueTask.CompletedTask` and `default` become `Task.CompletedTask` (or
`Task.FromResult<T>(default!)`), `Unit.ValueTask` becomes `Task.FromResult(Unit.Value)`, and a `ValueTask` of
your own, such as a call to a private helper, gets `.AsTask()`.

The registration:

| `MediatorOptions` | `RelevoxOptions` |
|---|---|
| `ServiceLifetime`, `Singleton` unless set | `Lifetime` and `HandlerLifetime`, both written out, and the lifetime of each behaviour |
| `PipelineBehaviors = [typeof(A<,>), ...]` | one `AddOpenBehavior(typeof(A<,>), lifetime)` each, in the same order; `AddBehavior` for a closed type |
| `StreamPipelineBehaviors` | `AddOpenStreamBehavior` and `AddStreamBehavior` |
| a `MessageExceptionHandler` subclass in `PipelineBehaviors` | left out, when the fix can see the class derives from `MessageExceptionHandler`, directly or through a class of yours: Relevox finds exception handlers at build time |
| `NotificationPublisherType = typeof(ForeachAwaitPublisher)` or `TaskWhenAllPublisher`, Mediator's | Relevox's publisher of that name |
| `NotificationPublisherType = typeof(YourPublisher)` | the same line, whatever the class is called; the class is rewritten by hand |
| `Namespace`, `GenerateTypesAsInternal`, `Assemblies` | dropped: Relevox finds handlers in the project and everything it references |

The trial's registration, as the fix left it:

```diff
-services.AddMediator(options =>
+services.AddRelevox(options =>
 {
-    options.Assemblies = [typeof(DependencyInjection), typeof(DomainEvent)];
+    options.Lifetime = ServiceLifetime.Scoped;
+    options.HandlerLifetime = ServiceLifetime.Scoped;
+    options.AddOpenBehavior(typeof(ValidationBehavior<,>), ServiceLifetime.Scoped);
+    options.AddOpenBehavior(typeof(PerformanceBehaviour<,>), ServiceLifetime.Scoped);
+    options.AddOpenBehavior(typeof(FusionCacheBehaviour<,>), ServiceLifetime.Scoped);
+    options.AddOpenBehavior(typeof(CacheInvalidationBehaviour<,>), ServiceLifetime.Scoped);
     options.NotificationPublisherType = typeof(ChannelBasedNoWaitPublisher);
-    options.ServiceLifetime = ServiceLifetime.Scoped;
-    options.PipelineBehaviors = [
-        typeof(FallbackExceptionHandler<,>),
-        typeof(ValidationExceptionHandler<,>),
-        typeof(NotFoundExceptionHandler<,>),
-        typeof(DbExceptionHandler<,>),
-        typeof(ValidationBehavior<,>),
-        typeof(PerformanceBehaviour<,>),
-        typeof(FusionCacheBehaviour<,>),
-        typeof(CacheInvalidationBehaviour<,>)
-    ];
 });
```

An options object passed in, a method group, a lifetime written as anything but a name or a member access (a
method call or a conditional, say; `ServiceLifetime.Scoped` and `Settings.Lifetime` are fine), a behaviour list
not written as `typeof(...)`, and a lambda with a comment or `#if` in it get no fix; the [RVX0017 page](diagnostics.md#rvx0017)
lists those cases.

## 4. What the fix leaves

Each of these is a compiler error after step 3, except where it says otherwise.

### Exception handlers

A `MessageExceptionHandler` subclass becomes an `IRequestExceptionHandler`. The exception type becomes a type
parameter constrained to the class it was, because Relevox registers a generic exception handler only when its
type parameters are exactly the interface's: one with a fixed exception type, such as
`IRequestExceptionHandler<TRequest, TResponse, DbUpdateException>` on a class with two type parameters, is
reported as [RVX0004](diagnostics.md#rvx0004) and not registered at all, which is a warning, not an error.

```diff
-public sealed class DbExceptionHandler<TRequest, TResponse> : MessageExceptionHandler<TRequest, TResponse, DbUpdateException>
-    where TRequest : IRequest<TResponse>
+public sealed class DbExceptionHandler<TRequest, TResponse, TException> : IRequestExceptionHandler<TRequest, TResponse, TException>
+    where TRequest : notnull, IRequest<TResponse>
+    where TException : DbUpdateException
     where TResponse : IResult
 {
-    protected override ValueTask<ExceptionHandlingResult<TResponse>> Handle(TRequest request, DbUpdateException exception, CancellationToken cancellationToken)
+    public Task Handle(TRequest request, TException exception, RequestExceptionHandlerState<TResponse> state, CancellationToken cancellationToken)
     {
         var errors = GetUserFriendlyErrors(exception);
         var failureResult = CreateFailureResult(errors);
-        return Handled(failureResult);
+        state.SetHandled(failureResult);
+        return Task.CompletedTask;
     }
```

A path that returned Mediator's not-handled result returns `Task.CompletedTask` without calling `SetHandled`. The
interfaces are in `Relevox.Pipeline`, which needs a `using`; the trial added a `global using`. Nothing is
registered: Relevox finds the class at build time. The fix has already taken it out of the behaviours when it
could see the class derives from `MessageExceptionHandler`. When it could not, because the `typeof` names
something it cannot resolve, the registration keeps an `AddOpenBehavior` line for it; delete that line, since
`AddOpenBehavior` throws for a type that is not a behaviour.

**A catch-all for `Exception` is different.** Mediator runs exception handlers where they stand in the list
of behaviours, so a catch-all listed first only sees what the handlers inside it did not handle. Relevox tries
exception handlers [from the thrown type up to `Exception`](compatibility.md#the-pipeline), and a handler for
`Exception` is also tried at every more specific step another handler names, in metadata order. In the trial,
moved as an exception handler, the catch-all answered a `ValidationException` before the validation handler
did, and the error messages came back in the catch-all's format. To keep Mediator's order, make it a behaviour
that runs outside Relevox's exception handlers, and register it again:

```csharp
[PipelineOrder(-1)]
public sealed class FallbackExceptionHandler<TRequest, TResponse> : IPipelineBehavior<TRequest, TResponse>
    where TRequest : IRequest<TResponse>
    where TResponse : IResult
{
    public async Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken cancellationToken)
    {
        try
        {
            return await next(cancellationToken).ConfigureAwait(false);
        }
        catch (Exception exception)
        {
            // what the old Handle did, returning the response instead of Handled(response)
        }
    }
}
```

```csharp
options.AddOpenBehavior(typeof(FallbackExceptionHandler<,>), ServiceLifetime.Scoped);
```

A behaviour with a negative `[PipelineOrder]` runs outside the exception handlers
([ADR 0019](adr/0019-pipeline-order.md)).

### A notification publisher of your own

Relevox's `INotificationPublisher` gets every handler for the notification at once, as executors, and returns a
`Task`:

```diff
-public async ValueTask Publish<TNotification>(NotificationHandlers<TNotification> handlers, TNotification notification, CancellationToken cancellationToken)
-    where TNotification : INotification
+public async Task Publish(IEnumerable<NotificationHandlerExecutor> handlers, INotification notification, CancellationToken cancellationToken)
 {
     foreach (var handler in handlers)
     {
-        await handler.Handle(notification, cancellationToken);
+        await handler.HandlerCallback(notification, cancellationToken);
     }
 }
```

Tests that built Mediator's `NotificationHandlers<T>` to call the publisher directly build executors instead:
`new NotificationHandlerExecutor(handler, (n, ct) => handler.Handle((T)n, ct))`.

### Razor

`@using Mediator` in `_Imports.razor` becomes `@using Relevox`. Code fixes cannot reach Razor files, and the build
reports every `IMediator` in them until this is done. `@inject IMediator Mediator` and `await Mediator.Send(...)`
need nothing else.

### `ValueTask` where you call the mediator

`Send` and `Publish` return `Task` in Relevox. Awaiting code needs nothing. Code that names the type does: in the
trial, a Moq setup of `IMediator.Publish` with `.Returns(ValueTask.CompletedTask)`, which becomes
`.Returns(Task.CompletedTask)`. Variables, fields and parameters typed `ValueTask` are not touched by the fix
either.

### Not met in the trial

These are listed in [ADR 0024](adr/0024-moving-from-mediator.md) and get no fix; the trial application did not
have them, so this page does not claim more than the names:

- `MessagePreProcessor` and `MessagePostProcessor` subclasses. Relevox's are `IRequestPreProcessor<TRequest>` and
  `IRequestPostProcessor<TRequest, TResponse>`, in `Relevox.Pipeline`, each with a `Process` method returning
  `Task`. They are not registered from the behaviour list: register them with `AddRequestPreProcessor` and its
  siblings, or set `AutoRegisterRequestProcessors`. If they were in `PipelineBehaviors`, the fix kept an
  `AddOpenBehavior` line for each; delete it.
- `[assembly: MediatorOptions]`: move what it set into the `AddRelevox` call.
- A behaviour that passes a different message to `next`. The fix moves the behaviour, its signature and its
  other calls included, and leaves only the `next(other, cancellationToken)` call, which Relevox's pipeline,
  carrying one request, cannot express; the compiler points at it.

## 5. Test projects and other `AddMediator` calls

A test project that called `AddMediator` to build a mediator of the application's now calls its own
`AddRelevox`, because the application's is `internal`. That builds a second mediator, and the trial showed both
ways it goes wrong:

- With the application's mediator already registered, through the application's own registration method,
  `AddRelevox` throws: *IMediator is already registered, probably by AddRelevox from another project.*
- Without it, the test project's mediator has none of the application's handlers, and a published notification
  reaches nobody. The build warns with [RVX0005](diagnostics.md#rvx0005).

The fix is to register the mediator the way the application does. In the trial, the application calls
`AddRelevox` inside its own `AddApplication()`, so the tests call that and nothing else:

```diff
-services.AddRelevox(options =>
-{
-    options.Lifetime = ServiceLifetime.Scoped;
-    options.HandlerLifetime = ServiceLifetime.Scoped;
-    options.NotificationPublisherType = typeof(ChannelBasedNoWaitPublisher);
-});
+services.AddApplication();
```

A test project that declares handler classes of its own, as test doubles, still generates an unused mediator
and keeps the RVX0005 warning about the application's handlers. Its advice, to reference `Relevox.Contracts`
from the application, does not apply when the application is the one that calls `AddRelevox`; suppress the
warning in the test project.

## 6. What behaves differently

- **Handler lifetime.** Mediator's `ServiceLifetime` is `Singleton` unless set, and applies to the mediator, the
  handlers, the behaviours and the notification publisher. Relevox's settings are transient unless set. The fix
  writes Mediator's lifetime out everywhere it applied, so nothing changes until you change it. A handler that
  is scoped or singleton is resolved once per mediator instance and kept, as `RelevoxOptions.HandlerLifetime`
  describes.
- **`ValueTask` becomes `Task`.** Handlers, behaviours, `Send` and `Publish` all return `Task`. A handler that
  finishes synchronously now allocates its task ([ADR 0023](adr/0023-no-valuetask-handlers.md)).
- **Commands and queries are requests.** Relevox dispatches by type, so nothing depended on the distinction; it
  is gone from the names. Declare `ICommand<T> : IRequest<T>` yourself if you want the words back.
- **Exception handlers run outside every behaviour**, and are tried by exception type rather than by their place
  in the list of behaviours, as described [above](#exception-handlers). In the trial this changed which handler
  answered a validation failure, until the catch-all was made a behaviour.
- **Notification publishing.** Both libraries default to running handlers one after another,
  `ForeachAwaitPublisher`. A publisher of your own is created with the mediator's lifetime in both, and in Relevox
  receives one executor per handler, in metadata order. The trial's publisher, which queues handlers on a channel
  and returns at once, kept its behaviour, and its own tests for that passed.
- **One `AddRelevox` per application.** `AddMediator` is public and generated once; `AddRelevox` is `internal`
  and generated per calling project, so the projects that need the mediator get it through a method of the
  project that calls `AddRelevox` ([step 5](#5-test-projects-and-other-addmediator-calls)).
- **The build checks more.** The first build reports what Mediator would have reported differently or not at
  all: [RVX0001](diagnostics.md#rvx0001) for a request with no handler, [RVX0004](diagnostics.md#rvx0004) for a
  generic handler it cannot register, [RVX0005](diagnostics.md#rvx0005) for a mediator in the wrong project. The
  [MediatR guide](migration.md#4-build-and-read-what-it-reports) has the full list; Relevox's behaviour after the
  move is MediatR 12's, described in [compatibility.md](compatibility.md).
