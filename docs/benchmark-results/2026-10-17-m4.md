# M4: performance

Same machine and harness as before, measured after the M4 review fixes:

```
BenchmarkDotNet v0.15.8, Windows 11 (10.0.26100.9448/24H2)
Intel Core Ultra 7 255H 2.00GHz, 16 logical and 16 physical cores
.NET SDK 10.0.402, runtime .NET 10.0.13, X64 RyuJIT x86-64-v3, DefaultJob
```

M2 left two rows weak: the pipeline with three behaviours (0.61 of MediatR) and streams (about even with
MediatR). M4 worked on both, and added the scale benchmark the plan promised.

## Where M4 moved the numbers

| | M2 | M4 | Mediator 3.0 |
|---|---:|---:|---:|
| Send with three behaviours, ratio to MediatR | 0.61, 544 B | **0.47, 392 B** | 0.08 |
| Stream of 100 items, ratio to MediatR | 1.12, 416 B | **0.57, 328 B** | 0.50 |

**Pipeline.** Each behaviour's `next` used to be a delegate on a small object that remembered which step came
next, plus an array caching those delegates. For the first eight behaviours the delegates now point at
methods on the chain object itself. What is left is what the design requires: the behaviours the container
creates on each send, the array it returns them in, the chain, and one delegate per behaviour. Mediator
composes its behaviours at build time and holds them as singletons, which no amount of tuning reproduces
without giving up behaviours resolved from the container.

**Streams.** Every item used to pass through a second async iterator, there to resolve the handler when
enumeration starts and to combine the `CreateStream` token with a `WithCancellation` token, as MediatR does.
A hand-written enumerator now does both on the first `MoveNextAsync` and then forwards every item straight to
the handler's enumerator. Streams went from even with MediatR to within 15% of Mediator, which returns the
handler's stream untouched and does neither of those things.

## 500 request types

A separate assembly with five hundred requests and handlers per library
([`benchmarks/Capar.Benchmarks.Scale`](../../benchmarks/Capar.Benchmarks.Scale)). Every library runs with
transient handlers here, so for the first time Mediator is compared like for like: it reads its lifetime at
compile time, which the main benchmark project cannot vary.

| | Mean | Error | Ratio | Allocated |
|---|---:|---:|---:|---:|
| MediatR 12.5 | 37.7 ns | 0.6 ns | 1.00 | 128 B |
| **Çapar, typed** | **9.5 ns** | 0.2 ns | **0.25** | 24 B |
| **Çapar, ISender** | **18.7 ns** | 0.4 ns | **0.50** | 24 B |
| Mediator 3.0 transient, typed | 28.3 ns | 0.5 ns | 0.75 | 88 B |
| Mediator 3.0 transient, ISender | 35.1 ns | 0.7 ns | 0.93 | 88 B |
| MediatR 12.5, eight types in turn | 113.5 ns | 2.0 ns | 3.01 | 184 B |
| **Çapar, ISender, eight types in turn** | **28.2 ns** | 0.6 ns | **0.75** | 24 B |
| Mediator 3.0 transient, ISender, eight types in turn | 113.4 ns | 1.4 ns | 3.01 | 88 B |

Three things in this table:

- **The interface path does not grow with the project.** Çapar's `ISender` send costs 15.7 ns with one
  request type and 18.7 ns with five hundred. fastcast's routing method was twice as slow as MediatR at five
  hundred types; a dispatcher per type in a frozen dictionary fixed that.
- **With the same lifetimes, Çapar is faster than Mediator.** Mediator's sub-nanosecond typed send in the
  main benchmarks comes from holding singleton handlers. With transient handlers, as MediatR and Çapar
  default to, its typed send is 28.3 ns against Çapar's 9.5 ns.
- **Sending one hot request flatters every library.** The rotating rows send eight different request types
  in turn. MediatR and Mediator both go from about 35 ns to 113 ns; Çapar goes from 18.7 ns to 28.2 ns.

## What is left

- **Built-in behaviours are created on every send that has a pipeline.** Since fixed; see
  [the built-ins results](2026-10-18-built-ins.md). The exception and processor
  behaviours MediatR registers are resolved with the user's behaviours, even when no processor or exception
  handler exists for the request, so they cost an allocation each and do nothing. Skipping them needs the
  generator to know, per request, that none of their inputs exist; the container can still add one at run
  time, so that is not free to prove.
- **One stream exception arrives differently.** From the second item on, a hand-written enumerator that
  throws synchronously from `MoveNextAsync` reaches the caller as a throw rather than a faulted task. An
  `await foreach` cannot tell the two apart; code that calls `MoveNextAsync` by hand and inspects the task
  can.

## The plan's hypotheses, final

| Hypothesis | Result |
|---|---|
| Typed `Send` with no behaviours allocates nothing beyond the handler | Confirmed: 24 B, the transient handler |
| Typed `Send` takes at most half of MediatR's time | Confirmed: 0.25 |
| Interface `Send` no slower than MediatR at 1 and at 500 request types | Confirmed: 0.42 and 0.50; 0.25 of MediatR when request types vary |
| With singleton handlers, typed `Send` within 2x of Mediator | Confirmed: 0.48 ns against 1.10 ns |
| Cold start faster than MediatR | Confirmed: 0.03 |
