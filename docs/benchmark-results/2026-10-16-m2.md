# M2: the pipeline

Same machine and harness as the [baseline](2026-10-16-baseline.md) and [M1](2026-10-16-m1.md), measured after
the M2 review fixes:

```
BenchmarkDotNet v0.15.8, Windows 11 (10.0.26100.9448/24H2)
Intel Core Ultra 7 255H 2.00GHz, 16 logical and 16 physical cores
.NET SDK 10.0.402, runtime .NET 10.0.13, X64 RyuJIT x86-64-v3, DefaultJob
```

The machine was noisier than for M1: MediatR's own send measured 41.3 ns against 33.1 ns earlier the same
day, with no change on its side. Compare ratios to MediatR within this run rather than absolute numbers
across runs.

## Send, no behaviours

| | Mean | Ratio | Allocated |
|---|---:|---:|---:|
| MediatR 12.5 | 41.3 ns | 1.00 | 128 B |
| **Relevox, typed** | **10.2 ns** | **0.25** | **24 B** |
| Relevox, ISender | 16.0 ns | 0.39 | 24 B |
| Relevox, `Send(object)` | 22.2 ns | 0.54 | 120 B |
| Relevox singletons, typed | 0.48 ns | 0.01 | 0 B |
| Relevox singletons, ISender | 7.8 ns | 0.19 | 0 B |
| Mediator 3.0, typed | 1.24 ns | 0.03 | 0 B |
| Mediator 3.0, ISender | 5.0 ns | 0.12 | 0 B |

The no-behaviour path is where it was in M1 (0.25 against 0.23), even though every send now first checks
whether the request has behaviours. That check is one byte read, and it stays cheap only because the send
method is small enough to inline. The first M2 run had the code that turns a synchronous throw into a
faulted task inside the send itself; a method with an exception handler is never inlined, and the singleton
send went from 0.46 ns to 1.9 ns. Moving that code into a helper the direct path never reaches brought it
back to 0.48 ns.

## Send with three behaviours

| | Mean | Ratio | Allocated |
|---|---:|---:|---:|
| MediatR 12.5 | 143.6 ns | 1.00 | 656 B |
| **Relevox, typed** | **86.4 ns** | **0.61** | **544 B** |
| Mediator 3.0, typed | 13.3 ns | 0.09 | 0 B |

This is the weakest row and the reason is a design choice. Behaviours are resolved from the container on
every send, as MediatR resolves them, so behaviours registered directly with the container, open generic
behaviours and scoped behaviours all keep working. That costs three transient behaviour objects, the array
the container returns, and one chain link per behaviour. Mediator composes its behaviours at build time and
holds them as singletons, which is why it is an order of magnitude faster and also why it cannot see a
behaviour registered after the build. Narrowing the gap without losing that is M4 work.

## Stream of 100 items

| | Mean | Ratio | Allocated |
|---|---:|---:|---:|
| MediatR 12.5 | 2.85 µs | 1.00 | 592 B |
| Relevox, typed | 3.16 µs | 1.12 | 416 B |
| Mediator 3.0, typed | 1.33 µs | 0.47 | 200 B |

Streams are no faster than MediatR, and in this run slightly slower. The MediatR-compatible wrapper iterator
from M1 costs about 12 ns per item, and the stream now also asks the pipeline state about stream behaviours
when enumeration starts. This is the other M4 item.

## Register, build the container, send once

| | Mean | Ratio | Allocated |
|---|---:|---:|---:|
| MediatR 12.5 | 121.3 µs | 1.00 | 351 KB |
| **Relevox** | **4.1 µs** | **0.03** | **14 KB** |
| Mediator 3.0 | 18.7 µs | 0.15 | 49 KB |

Startup grew from M1 because `AddRelevox` now registers the pipeline state and the publisher, and builds the
lookup tables that keep registration linear in the number of handlers.
