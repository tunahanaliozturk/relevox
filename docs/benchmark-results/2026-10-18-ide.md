# What the generator costs while you type

The runtime numbers elsewhere in this folder are about the application. This page is about the IDE: the
generator and the analyzer run inside the compiler, and in an editor they run again as code changes.

Same machine as the other results: Intel Core Ultra 7 255H, .NET SDK 10.0.402, Roslyn 5.0 as shipped with it.

## A full build

A two-project solution generated for the purpose: a library with 2,000 requests and handlers, 500
notifications with handlers, 10 generic request handlers and one generic notification handler, and a host with
500 more requests and handlers that calls `AddCapar`. Built with `-p:ReportAnalyzer=true`, which makes the
compiler time every analyzer and generator.

| In the host's compilation | Time |
|---|---:|
| Çapar's generator | 0.54 s |
| Çapar's analyzer (CPR0001 to CPR0006) | 0.14 s, 4% of analyzer time |
| The migration analyzer (CPR0007) | under 1 ms |
| All analyzers, .NET's own included | 2.85 s |

The application ran and dispatched to a handler in the library and to a generic handler closed at build time.

## An edit

What matters in an editor is the cost of one more change. This was measured with Roslyn's generator driver on
a single project of N requests and N handlers and no generic handler, editing an unrelated method body 60 times
and taking the median of the last 20, after the JIT had settled. The harness is
`tests/Capar.SourceGenerator.Tests/EditCostMeasurement.cs`; it only runs when asked:

```bash
dotnet run --project tests/Capar.SourceGenerator.Tests -c Release -- -explicit only
```

The table is the middle of three runs; runs differ by about 15%.

| Handlers in the project | Per edit | Of which discovery in source | Of which closing generics |
|---:|---:|---:|---:|
| 500 | 18 ms | 15 ms | 1 ms |
| 2,500 | 102 ms | 90 ms | 2 ms |

Two changes came out of measuring this.

- **The step that closes generic handlers walked every type's interfaces on every edit,** whether or not the
  project had a generic handler: 181 ms of the 2,500-handler edit. It now finds generic handler definitions
  first, which only asks generic types for their interfaces, and looks no further when there are none. A
  project with a generic handler still pays for the walk on every edit.
- **Walking a compilation's types built every member of every type.** The walk asked each type for all of its
  members to find nested types, which made the compiler create every method and property symbol. It now asks
  for nested types only.

What is left is discovery in source: Roslyn runs the semantic step of a syntax provider again for every
matching declaration whenever the compilation changes, and every request, notification and handler is one.
Its output compares equal when nothing relevant changed, so nothing after it runs again and no code is
regenerated. Visual Studio can also run source generators only when a file is saved or the project built,
its "Balanced" execution setting, which takes this off the typing path entirely.
