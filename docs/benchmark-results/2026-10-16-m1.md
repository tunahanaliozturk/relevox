# M1: Relevox against MediatR 12.5.0 and Mediator 3.0.2

First numbers with Relevox in the table, measured after the M1 review fixes. Same machine and harness as the
[baseline](2026-10-16-baseline.md):

```
BenchmarkDotNet v0.15.8, Windows 11 (10.0.26100.9448/24H2)
Intel Core Ultra 7 255H 2.00GHz, 16 logical and 16 physical cores
.NET SDK 10.0.402, runtime .NET 10.0.13, X64 RyuJIT x86-64-v3, DefaultJob
```

Every row is checked by `--sanity` before it is measured. "Typed" means calling the generated mediator with
the request's own type; "ISender" means calling through the interface, which is what code migrated from
MediatR does unless it is changed. Relevox runs with its defaults (transient handlers, as MediatR) and, in the
"singletons" rows, with `HandlerLifetime = Singleton`, which is Mediator's default.

## Send, no behaviours

| | Mean | Allocated |
|---|---:|---:|
| MediatR 12.5 | 33.1 ns | 128 B |
| **Relevox, typed** | **7.5 ns** | **24 B** |
| Relevox, ISender | 11.0 ns | 24 B |
| Relevox, `Send(object)` | 16.7 ns | 120 B |
| Relevox singletons, typed | 0.46 ns | 0 B |
| Relevox singletons, ISender | 4.9 ns | 0 B |
| MediatR 12.5, `Send(object)` | 37.8 ns | 224 B |
| Mediator 3.0, typed | 0.91 ns | 0 B |
| Mediator 3.0, ISender | 4.1 ns | 0 B |
| Mediator 3.0, `Send(object)` | 10.8 ns | 24 B |

The 24 B in Relevox's transient rows is the handler: a new `PingHandler` per call, which MediatR allocates
too. Relevox itself allocates nothing on these paths.

## Publish

| | Mean | Allocated |
|---|---:|---:|
| MediatR 12.5, 1 handler | 51.8 ns | 288 B |
| **Relevox, 1 handler** | **11.1 ns** | **24 B** |
| Mediator 3.0, 1 handler | 1.9 ns | 0 B |
| MediatR 12.5, 5 handlers | 132.4 ns | 896 B |
| **Relevox, 5 handlers** | **50.5 ns** | **120 B** |
| Mediator 3.0, 5 handlers | 15.2 ns | 0 B |

Again the allocation is five transient handlers at 24 B each.

## Stream of 100 items, drained

| | Mean | Allocated |
|---|---:|---:|
| MediatR 12.5 | 2.61 µs | 592 B |
| Relevox, typed | 2.49 µs | 416 B |
| Mediator 3.0, typed | 1.26 µs | 200 B |

Relevox is barely faster than MediatR here, and that is a decision, not an accident. The differential tests
showed that MediatR wraps every stream in an iterator of its own, which is why its handler is resolved
lazily and why a caller's `WithCancellation` token reaches handlers that do not declare
`[EnumeratorCancellation]`. Relevox matches both, so it pays for the same extra iterator, about 12 ns per item.
Mediator returns the handler's stream as is and is twice as fast. Narrowing that gap without giving up the
semantics is an M4 question.

## Register, build the container, send once

| | Mean | Allocated |
|---|---:|---:|
| MediatR 12.5 | 78.9 µs | 344 KB |
| **Relevox** | **1.5 µs** | **10 KB** |
| Mediator 3.0 | 11.9 µs | 49 KB |

No assembly scan, and `AddRelevox` is a flat list of registrations.

## The plan's hypotheses

| Hypothesis | Result |
|---|---|
| Typed `Send` with no behaviours allocates nothing beyond the handler | Confirmed: 24 B, the transient handler |
| Typed `Send` takes at most half of MediatR's time | Confirmed: 0.23 of MediatR |
| Interface `Send` no slower than MediatR at 1 and at 500 request types | Confirmed at 1 (0.33). 500 is measured in M4 |
| With singleton handlers, typed `Send` within 2x of Mediator's typed send | Confirmed: 0.46 ns against 0.91 ns |
| Cold start faster than MediatR's | Confirmed: 1.5 µs against 78.9 µs |

Pipeline behaviours arrive in M2, so the pipeline table still has no Relevox row.
