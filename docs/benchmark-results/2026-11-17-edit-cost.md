# What an edit costs the generator, in the layouts the first measurement missed

A follow-up to [2026-10-18-ide.md](2026-10-18-ide.md), for #166. That measurement had a hundred handlers to a
file, nothing sent and no generic handler. Reading the pipeline suggested all three hide cost, so the harness
gained rows for them first, and each change below was measured against them.

Intel Core Ultra 7 255H, .NET SDK 11.0.100, the harness run on .NET 10.0.15, Roslyn 5.0.0.

## How it was measured

The harness is `tests/Relevox.SourceGenerator.Tests/EditCostMeasurement.cs`, unchanged in method: Roslyn's
generator driver on one project, an unrelated method body edited 60 times, the median of the last 20 edits. Step
tracking is on, to split the time by step, so the totals are a little higher than an editor would see.

```bash
dotnet run --project tests/Relevox.SourceGenerator.Tests -c Release -f net10.0 -- -explicit only -class "*EditCostMeasurement"
```

The rows it adds:

- **A file each**: every request and its handler in a file of its own, 2,500 files, as most projects are laid out.
- **Sends**: next to each request, a class without a base list that sends it through `ISender`, 2,500 calls.
- **Generic**: ten generic request handlers, each closed over ten entity classes.

Each change was built into its own copy of the test binary, and the copies were run in turn, before, after,
before, after, three rounds, in one session. The machine was not quiet: other programs were using several cores
during every round, as Windows' performance counters showed at the time. Two sessions running the same binary
differ by up to a quarter on the slowest row (1,339 against 1,062 ms below), so only the comparisons inside one
session are worth reading, and only differences well beyond that spread are claimed.

The first four rows are the old layout and land near the published 18 and 102 ms when the machine is quiet (the
first run gave 22 and 112). A file each costs three times as much per edit as a hundred to a file. Sending each
request from a class beside it costs most of a second more, whether or not the map is on: that is the call site
step, which this version of the harness could not time on its own because its tracking name sat on a later step.

## Call sites bound only when the map is asked for

The call site provider bound every `Send`, `Publish` and `CreateStream` call on every edit, so a project paid for
the message map's call sites with the map off, the default. The provider now only finds candidate calls from
syntax, which Roslyn redoes for a changed file alone, and the map step binds them when the map is on (commit
`9e33271`).

| Row, 2,500 handlers, a file each | Before, three runs | After, three runs |
|---|---|---|
| sends, map off | 854, 1,366, 1,326 | 600, 570, 549 |
| sends, generic, map off | 1,147, 1,329, 1,334 | 489, 546, 443 |
| sends, map on | 1,305, 1,466, 1,219 | 1,339, 1,309, 1,370 |
| nothing sent, map off | 354, 514, 481 | 612, 509, 455 |

Kept. With the map off an edit costs about 60 per cent less in a project that sends from 2,500 places, and the
runs do not overlap. With the map on the binding moves into the map step (89 to 104 ms before, 783 to 857 ms
after) and the total stays where it was. A project that sends nothing is unaffected, as expected; its two sets of
runs overlap.

## The tree index looked up once per compilation

`OrderOf` found a handler's file by walking the compilation's syntax trees, once per handler, which grows with
handlers times files. The positions are now built once per compilation and looked up (commit `ce7b676`).
Measured against the call site change, in a second session:

| Row, 2,500 handlers, a file each | Before, three runs | After, three runs |
|---|---|---|
| nothing sent, map off | 453, 440, 376 | 340, 390, 423 |
| sends, map off | 506, 472, 405 | 343, 452, 427 |
| sends, map on | 1,086, 1,008, 1,062 | 1,031, 1,066, 946 |
| sends, generic, map off | 452, 481, 804 | 467, 517, 431 |

Not visible. The runs overlap on every row. Timed directly, the old walk costs 0.9 ms per edit at 2,500 files and
2,500 handlers (the profile below), well inside the noise of a 300 to 450 ms edit. It is kept anyway: it is no
more code than the walk was, and the walk grows with handlers times files: at ten thousand of each it would be
about 15 ms.

## Where the per-declaration step spends its time

The semantic step of the source syntax provider is most of every row above. To see inside it, a build of the
generator with timers around each part was run on two layouts, 2,500 handlers each, every request sent from a
class beside it, map off, after both changes above. The timers and the scratch test that read them were not
committed. Two runs each, milliseconds per edit:

| Part | 100 to a file | A file each |
|---|---:|---:|
| Whole edit | 111, 112 | 317, 304 |
| The source step, as Roslyn times it | 98, 95 | 282, 270 |
| `GetDeclaredSymbol` | 6, 7 | 46, 38 |
| `AllInterfaces`: the compiler binding each type's base list | 30, 34 | 154, 141 |
| Type names and shapes (`ToDisplayString` and the telemetry names) | 28, 27 | 35, 40 |
| Accessibility, `[Obsolete]` and `[Experimental]` checks on the handled types | 7, 7 | 10, 9 |
| The generated code check | 1.4, 1.6 | 2.1, 2.2 |
| Location, own accessibility, declaration order | under 2 | under 4 |
| The old tree walk, for comparison | 0.0, 0.0 | 0.9, 0.9 |

Asking the compiler for the declared symbol and its interfaces is about 40 per cent of the step in the old layout
and over 60 per cent in a file each: for the same 5,000 declarations it costs four to five times as much spread
over 2,500 files as over 25. Any discovery that asks a type what it implements pays it. Avoiding the question for most types means filtering by
name, which misses handlers reached through a base class, through an interface of the project's own that
extends `IRequestHandler`, and partial types, so it is out of scope for #166.

What is left in the generator's own code was tried and not taken:

- **Building the handled message's shape once.** A handler built the shape of its message, then the same shape
  again for the message's dispatch entry. Reusing it, together with the next item, gave a names column of 29 and
  18 ms in the old layout and 30 and 21 ms in a file each, and whole edits of 123 and 112 ms and of 274 and
  281 ms. That is ten milliseconds at best, under the noise of either layout, so it is left out.
- **Comparing namespaces by name.** Each Relevox interface's namespace was turned into a string twice to compare
  it. Comparing the names instead made no difference that showed, since only interfaces from Relevox.Contracts
  get that far.
- **Caching across edits.** Every edit is a new compilation with new symbols, so nothing keyed on a symbol
  survives to the next one, and a cache keyed on syntax would have to know which edits change a type's
  interfaces, which is the question the compiler is being asked.

## What is left

An edit in a 2,500-handler project laid out a file each costs about 350 to 450 ms of generator time on this
machine as it was, most of it the compiler binding base lists. With the message map on, binding the call sites
adds about 600 to 850 ms for 2,500 calls; the map is off by default. Visual Studio's "Balanced" source generator setting, which runs generators on save or build, takes
both off the typing path.
